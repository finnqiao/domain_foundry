## Design Specificity Verdict

**Low-to-medium specificity.** The trust model is distinctive—raw capture, routing receipts, review diffs, provenance, and correction history—but the shell is structurally a generic admin dashboard. A hobby’s identity is mostly an emoji, title, generic cards, and tabs. It does not yet feel like personal software created for that hobby.

The experiential mismatch is larger than the visual one. The promise is “Describe your passion. Get an app. Talk to it,” but the shell has no domain-creation conversation. The empty state asks users to describe a passion and then only offers starter installs; the composer performs ordinary capture.

**Deterministic scan:** three warnings, all `side-tab` accent-border patterns in `app/src/styles.css`: timeline card at line 541, overdue review item at line 806, and health card at line 877. The overdue and health borders are likely semantic false positives. The always-on timeline border is the strongest literal match. No direct finding occurred in `App.tsx`.

**Visual overlays:** unavailable. Browser discovery returned no browsers, so mutable injection and visual inspection did not run. No user-visible overlay is claimed.

## Overall Impression

The shell communicates calm operational competence but puts the harness ahead of the hobby. Its strongest quality is trust; its largest missed opportunity is turning that trust into a visible, emotionally satisfying transformation from one sentence to a useful personal app.

## What’s Working

1. **Trust is designed into several flows.** Read-only source preview, idempotency language, correction history, provenance, review diffs, and visible confidence make structured personal data inspectable.
2. **Feedback primitives are broadly present.** Busy labels, disabled controls, loading states, review counts, health status, receipts, and empty states provide a useful foundation.
3. **The block system is coherent.** Shared timeline, search, stats, planner, map, detail, and review patterns give the experience runtime a consistent starting point.

## Priority Issues

### [P0] The flagship creation task cannot be completed in the shell

**Why it matters:** This is the product promise and activation goal. The UI routes a domain description into ordinary capture, starter Install buttons call an endpoint that returns 410, and there is no creation wizard.

**Fix:** Make creation the dominant first-run action: one sentence → short hardening conversation → held-out test → app preview → first real capture → enter the app.

**Suggested command:** `$impeccable onboard`

### [P1] “Talk to it” is a context-free write box

**Why it matters:** The composer returns routing internals rather than a relationship with the hobby and disappears inside domain views. The timeline can instruct users to capture “above” where no composer exists.

**Fix:** Keep a domain-aware composer on every hobby surface, distinguish Log from Ask if both exist, and attach a one-click repair path to low-confidence outcomes.

**Suggested command:** `$impeccable clarify`

### [P1] The information architecture exposes operator machinery first

**Why it matters:** Six global destinations, every domain, eight starter cards, diagnostics, review mechanics, and developer docs make the app feel like infrastructure administration.

**Fix:** Center Today/Home, Your passions, and Inbox. Move Sources, Health, developer Docs, extensions, and backups under Settings or progressive disclosure.

**Suggested command:** `$impeccable distill`

### [P1] Trust feedback breaks at high-stakes moments

**Why it matters:** Receipts expose `unfiled`, `ledger`, object type, disposition, and confidence; review actions lack robust recovery; merge requires a raw UID; bulk decisions lack undo.

**Fix:** Translate receipts into plain language, add contextual correction, preserve failed work, replace raw identifiers with pickers/previews, and add a short undo window.

**Suggested command:** `$impeccable harden`

### [P1] Accessibility and mobile behavior are below release quality

**Why it matters:** The textarea removes focus outline, tabs lack arrow-key behavior, dialogs do not manage focus completely, map points lack a persistent keyboard alternative, touch targets are small, and mobile adaptation is incomplete.

**Fix:** Add a global focus-visible system, complete tab/dialog patterns, an accessible map list, 44px targets, and explicit phone layouts for navigation, sources, reviews, tables, and action bars.

**Suggested command:** `$impeccable audit`

## Persona Red Flags

### Jordan — confused first-timer

- Cannot find the control that fulfills “Describe your passion.”
- May type a domain request into Capture, receive `unfiled`/ledger language, and conclude setup failed.
- Sees “objects · views” and internal migration descriptions instead of hobby outcomes.
- Opens a domain and sees “Capture something above” without a composer.

### Sam — keyboard/screen-reader user

- The primary textarea has no visible focus treatment.
- Tab widgets lack roving focus and arrow navigation.
- Modal focus can escape and is not reliably restored.
- Map pins have no always-available keyboard/list equivalent.
- Compact buttons/chips are difficult motor-accessibility targets.

### Casey — distracted mobile user

- Navigation becomes a large wrapping header rather than a compact drawer or bottom pattern.
- Capturing requires leaving the active hobby, increasing context loss after interruption.
- Source import and review controls remain dense on narrow screens.
- Route state is not URL-backed, so refresh returns to Home.

## Minor Observations

- The sourdough placeholder remains visible for unrelated domains such as bouldering.
- Generated metadata uses implementation nouns (`objects`, `views`) rather than outcomes.
- Installing a starter silently closes the picker rather than opening the app and inviting the first capture.
- The three detector warnings are low priority compared with activation, behavior, and accessibility.

## Questions to Consider

1. Is “app” intended to mean domain-native software, or is a generic set of schema-driven views enough for v0.1?
2. Should the primary daily action be Capture, Ask, or a combined conversation with visibly different outcomes?
3. Should Health, Docs, and Review be primary destinations before a user has a successful hobby record?
4. What should the emotional peak be after the first sentence: a schema proposal, a ready app, or the first correctly structured real item?

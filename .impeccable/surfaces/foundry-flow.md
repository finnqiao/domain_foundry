# Foundry creation flow

## Mode

Operate

## Direction

**The Documentary Edit Bench.** Domain Foundry behaves like an evidence-led
editor: source material is logged before it is cut, three product concepts are
materially different edits of the same practice, remixing is an explicit splice,
and the approved cut becomes the application. Provenance is functional timecode,
not decoration.

## First viewport

The user's real practice and artifacts sit in a source monitor on the left. The
current build sequence runs across a restrained editing rail: Research, Three
Cuts, Remix, Model, Experience, Build, Proof. The right monitor shows the
currently selected artifact at usable scale. There is no chatbot transcript and
no generic metric-card dashboard.

## Information hierarchy

1. The current decision or task.
2. The evidence and user choice that justify it.
3. The three concept cuts or the selected application surface.
4. The derivation rail and quality state.
5. Advanced schema and implementation detail on demand.

## Signature interaction

The user drags or selects a workflow, schema fragment, interaction, or visual
system from another concept cut into the selected cut. The splice creates a
readable diff, records parentage, and immediately updates the model and preview
derived from the same `FoundrySpec`.

## System grammar

- Near-black editing room around warm paper source monitors; evidence uses cool
  slate, selected user decisions use amber, and release failures use explicit
  red text plus iconography.
- A compact neutral sans handles operation. Monospace is reserved for source
  locations, spec paths, hashes, and timecode-like derivation identifiers.
- Contact sheets and editing rails are real controls, not decorative cards.
- Motion is one authored splice: the borrowed fragment moves into the selected
  cut and the affected spec paths briefly resolve. Reduced motion swaps this for
  an immediate diff highlight.
- Narrow screens become one monitor with a persistent build rail and a bottom
  evidence drawer; no horizontal desktop timeline is forced onto mobile.

## Cross-surface reach

The creation flow, evidence inspector, remix history, and release report share
this world. Generated applications do not inherit it; each uses the visual world
encoded in its own evidence-backed experience specification.

## Risk and constraint

Film-editing language can obscure unfamiliar product-development terms. Every
metaphorical label therefore carries a plain domain label (for example, “Three
Cuts — product concepts”), and schema, accessibility, and release errors remain
literal. The metaphor never changes data-engineering vocabulary.

## Quality bars considered

- Crouwel construction grid: exceptionally legible derivation, but weaker at
  communicating lineage and remix as a user action.
- Variable-font specimen: strong live cause-and-effect, but overly centered on
  visual variation for a product whose critical differences include schema and
  workflow.
- Documentary edit bench: strongest combination of audience identification and
  product clarity because evidence, alternate cuts, local splices, provenance,
  and final output are native to the same working ritual.

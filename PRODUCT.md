# Product

<!-- impeccable:product-schema 1 -->

## Platform

web

## Stack

Existing Python 3.11+ local-first core with SQLite, FastAPI, declarative YAML
packs, and a React/Vite first-party application. Generated applications must
also have a self-contained owned export that does not depend on a hosted Domain
Foundry account.

## Users

Primary user — **inferred from the approved product goal:** a serious but
non-technical hobbyist or enthusiast who understands their practice but cannot
independently turn it into a sound data model and tailored application.

Secondary users are technical makers who want an inspectable starting point and
open-source contributors who add reviewed evidence, patterns, adapters, or
runtime capabilities.

## Product Purpose

Domain Foundry turns an interest, the person's real practice, and any artifacts
they already keep into an evidence-backed product concept, workload-fit schema,
distinctive usable experience, and owned local application.

Success is not generation alone. The user should receive an application that
models the domain accurately, supports its important workflows, explains why
important decisions were made, preserves correction and provenance, and can be
exported with its data, specification, evidence, and code.

## Positioning

The mechanism is an inspectable chain:

> reviewed domain evidence → competing product concepts → explicit remix →
> workload-derived domain model → experience specification → preview and app
> compiled from the same source → independent proof

The defensible repository is the reviewed knowledge fabric, typed specification,
compilers, and evaluation corpus. A coding harness or role-play prompt is not
the moat.

## Operating Context

- A user may begin by describing an interest, importing existing artifacts, or
  remixing an exemplar.
- Research is visible and cited. The user can distinguish evidence from a
  product hypothesis and from their own decision.
- The user compares three materially different concepts and may remix an entire
  concept or selected workflow, schema, interaction, or visual-system fragments.
- Schema review is expressed in domain language, realistic records, and user
  questions before raw implementation detail.
- The first completed act uses real user data and immediately produces a
  domain-specific payoff.
- Corrections preserve prior interpretation and become independent regression
  evidence.
- A technical user can inspect and export every artifact in the derivation.

## Capabilities and Constraints

- Packs remain declarative data by default; executable extensions require an
  explicit trust decision.
- Core owns safe validation, capture, provenance, correction, compilation, and
  adapter conformance. Core must not branch on domain names.
- Shared accessible primitives are encouraged; a single generic app shell is
  not an acceptable substitute for domain-specific task topology.
- Preview, local runtime, standalone export, migrations, and tests compile from
  one versioned `FoundrySpec`.
- The knowledge posture is **inferred from the approved plan:** curated,
  source-licensed reusable guidance plus cited live research for each build.
  Independent editorial review of the initial corpus is still required before
  a public-release claim.
- The ownership posture is **inferred from the approved plan:** an immediately
  usable Foundry app plus exportable code, data, evidence, and migrations.
- The system must be useful offline after creation. Live model and external data
  providers are optional adapters with explicit permissions and freshness.
- Generated output and imported evidence are untrusted until schema, license,
  policy, and security checks pass.

## Brand Commitments

The working name is **Domain Foundry**, but it is not cleared for public release:
a live exact-mark US application covers directly overlapping services. The
maintainer must select a replacement or document qualified clearance before the
brand is final. The screened replacement slate recommends **Patternstead**; see
[`docs/name-replacement-slate.md`](docs/name-replacement-slate.md).

The voice is direct, curious, and evidence-led. It should make professional
reasoning understandable without pretending the model is an infallible expert.
Do not describe generic scaffolds as finished personalized apps, and do not
fabricate users, outcomes, integrations, or benchmarks.

## Evidence on Hand

- Existing capture ledger, canonical records, provenance, corrections,
  policy-gated apply, local SQLite ownership, adapters, and conformance tests.
- Structured, cited reusable guidance in `knowledge/`; its independent
  editorial review is not yet complete.
- Three manually authored golden specifications in `examples/golden/`:
  Sourdough Lab, Card Collector, and Japanese Study Coach.
- Existing product-gap evidence in `docs/VISION_GAP_REVIEW_2026-08-08.md`.

There is not yet independent editorial review, external-user validation, an
external security review, a published package, or evidence that the general
generator meets the product promise. Future release copy must not imply those
gates have passed.

## Product Principles

1. Encode expertise as typed evidence, derivations, and gates rather than a
   staff-role prompt.
2. Be consistent in trusted primitives and non-uniform in domain experience.
3. Make identity, relationships, time, workloads, provenance, and evolution
   first-class schema decisions.
4. A preview is a promise: compile it and the final app from the same spec.
5. Ownership includes explanation, correction, export, restore, and exit.

## Accessibility & Inclusion

Generated web applications target WCAG 2.2 AA. Semantic structure, keyboard
operation, focus, text alternatives, status and error announcements, target
size, contrast, reflow, reduced motion, and critical manual screen-reader
journeys are release requirements rather than a final polish pass.
